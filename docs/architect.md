# Architecture Plan: Master Server + Client Binary

## Текущее состояние

Монолитный `apps/api` содержит всё вместе:
- Аутентификацию (GitHub OAuth, Better Auth)
- Управление песнями (yt-dlp, ffmpeg, локальное хранилище)
- Игровые сессии (WebSocket комнаты)
- Статистику и лидерборд
- Статику (спрайты, фоны)

Проблема: часть логики требует окружения пользовательской машины (браузер → куки YouTube), другая часть должна жить в облаке.

## Разделение модулей

### Остаётся в клиентском сервере (`apps/api` → бинарник)

| Модуль | Причина |
|--------|---------|
| `song/` | yt-dlp требует браузер хоста для куки |
| `sound/` | Локальные аудио-файлы |
| `scenes/` | Статика, спрайты |
| `game-session/` | WebSocket комната живёт на машине хоста |
| `health/` | Healthcheck локального сервера |
| `stats/` | Системные метрики (CPU, RAM) локальной машины |

### Переезжает на мастер сервер (`apps/master`)

| Модуль | Причина |
|--------|---------|
| `user/` | Глобальные профили, OAuth |
| `badge/` | GitHub-бейджи по глобальному рейтингу |
| Список комнат | Агрегация от всех клиентских серверов |
| Глобальный лидерборд | Сводная статистика со всех игр |
| История матчей | Постоянное хранилище результатов |

## Протокол: Клиент ↔ Мастер

Клиентский сервер при запуске **регистрируется** на мастере:

```
POST /rooms/register
{
  "host": "192.168.1.10:3000",   // публичный адрес клиента
  "name": "Fox's Karaoke Room",
  "maxPlayers": 4,
  "token": "<shared_secret>"     // для верификации
}
```

Мастер хранит список живых комнат и пингует их для healthcheck. Клиент шлёт результаты матча после окончания игры:

```
POST /matches/report
{
  "roomId": "...",
  "players": [...],
  "winner": "userId",
  "wpm": { "userId": 120, ... }
}
```

## Аутентификация

Поскольку OAuth живёт на мастере, клиентский сервер **не хранит** сессии. Схема:

1. Игрок логинится на мастере → получает JWT
2. При подключении к комнате передаёт JWT
3. Клиентский сервер верифицирует токен через публичный ключ мастера (без запросов к мастеру на каждый запрос)

## Структура монорепо (целевая)

```
apps/
  api/          → клиентский сервер (→ бинарник через bun build)
  master/       → мастер сервер (→ Render / Docker self-hosted)
  web/          → фронтенд (статика, раздаётся мастером или CDN)
  cli/          → инструменты для управления песнями
packages/
  ui/           → общие компоненты
  shared/       → общие типы/схемы (Room, Match, Player)
```

Пакет `packages/shared` важен — клиент и мастер должны использовать одни типы для протокола.

## Стратегия деплоя

### Официальный (облако)

| Сервис | Платформа | База данных |
|--------|-----------|-------------|
| Мастер сервер (`apps/master`) | Render (Web Service) | Turso (libsql) |
| Фронтенд (`apps/web`) | Render (Static Site) | — |

Render выбран за простоту CI/CD из GitHub и бесплатный tier для старта. Turso используется вместо локального SQLite — тот же Drizzle + libsql клиент, только `TURSO_CONNECTION_URL` переключает адрес.

```
GitHub push → Render build → деплой мастера + фронтенда
                                      │
                                      ▼
                              Turso (глобальная БД)
```

### Self-hosted (docker-compose)

`docker-compose.yml` предназначен для случаев когда нужно поднять **всю экосистему локально** — например на митапе, LAN-вечеринке или корпоративном мероприятии без доступа в интернет.

В этом режиме:
- Мастер сервер и фронтенд поднимаются в Docker
- База данных — локальный SQLite (Turso не нужен, `TURSO_CONNECTION_URL` не задан)
- Caddy раздаёт фронтенд и проксирует API на одном порту `:80`
- Клиентские серверы игроков — бинарники на их машинах, регистрируются на локальном мастере

```
LAN-сеть митапа
┌──────────────────────────────────────────────────────┐
│  Один ноутбук (docker compose up)                    │
│  └─ Мастер сервер + фронтенд на :80                 │
│                                                      │
│  Ноутбук игрока 1: ./lalasynth-server                │
│  Ноутбук игрока 2: ./lalasynth-server                │
│  Ноутбук игрока N: ./lalasynth-server                │
│                                                      │
│  Браузеры → http://<ip-хоста>/  (фронтенд)          │
└──────────────────────────────────────────────────────┘
```

### Сравнение режимов

| | Облако (Render) | Self-hosted (Docker) |
|---|---|---|
| БД | Turso | SQLite локальный |
| Фронтенд | Render Static Site | Caddy в Docker |
| Мастер | Render Web Service | Docker container |
| Клиент | Бинарник пользователя | Бинарник пользователя |
| Интернет | Требуется | Не требуется |
| Назначение | Постоянный продакшн | Митап / LAN |

## Замечания

**yt-dlp + куки**: Бинарник запускается на машине пользователя → `detectBrowser()` находит реальный браузер → куки YouTube доступны нативно. Проблема Docker с браузерами неактуальна для продакшена.

**Docker остаётся только для мастера**: Облачный деплой мастер-сервера через `docker compose` как сейчас, без yt-dlp и браузеров.

**Фронтенд**: Статика может раздаваться либо мастером (текущая схема с Caddy), либо отдельным CDN. Клиентский сервер фронтенд не раздаёт.
